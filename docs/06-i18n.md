# 06 — Multilingüe (i18n)

**Decisión (2026-09-16):** la app nace multilingüe. Se lanza solo en español, pero la estructura
para agregar idiomas existe desde el primer commit. Ningún texto visible vive hardcodeado en el
código.

## Por qué ahora

Agregar i18n a una app que ya tiene 300 strings sueltos es una semana de trabajo aburrido y
propenso a errores. Nacer con i18n cuesta casi nada: es una convención, no una feature.

## Idiomas

| Código | Estado | Notas |
|---|---|---|
| `es` | **default, único al lanzar** | Rioplatense, voseo ("adoptá", "registrate") |
| `pt-BR` | futuro | Brasil es el mercado vecino natural |
| `en` | futuro | Sin apuro |

No dividir el español en variantes (`es-UY`, `es-AR`, `es-ES`) hasta que exista una razón real.
`es` con voseo es el idioma fuente; si algún día hace falta un español neutro, se agrega como
variante nueva sin tocar `es`.

## Estructura

```
messages/
  es.json      ← idioma fuente, siempre completo
  pt-BR.json   ← (futuro) mismas claves
  en.json      ← (futuro) mismas claves
```

Librería candidata: **next-intl** (estándar de facto para Next.js App Router). Confirmar setup
actual en su documentación al momento de scaffoldear.

### Convenciones de claves

- **Namespaces por dominio**, no por pantalla: `common`, `auth`, `profile`, `verification`, `pets`,
  `applications`, `followup`, `admin`, `emails`, `legal`. El mensaje de texto del código vive en
  `verification.sms` y no en un namespace propio: es parte de la verificación, como el correo del
  enlace es parte del ingreso. Se escribe **sin á, í, ó ni ú** ("codigo"), porque una sola de esas
  letras parte el mensaje en dos y cuesta el doble; lo prueba `lib/sms/segments.test.ts`.
- **Claves semánticas**, nunca el texto: `pets.form.name_label`, no `"Nombre"`.
- **ICU para plurales y variables**: `"{count, plural, =0 {Sin solicitudes} one {# solicitud} other {# solicitudes}}"`.
- Sin concatenar strings en código. Si una frase tiene variables, va entera con placeholders.

### URLs

- Idioma default **sin prefijo**: `/`, `/animales/luna-123`.
- Otros idiomas con prefijo: `/pt-BR/animais/luna-123`.
- Motivo: los links se comparten por WhatsApp; cuanto más cortos y limpios, mejor.

### Qué se traduce (checklist)

- [ ] Textos de UI (botones, labels, errores, vacíos, tooltips)
- [ ] Emails transaccionales (magic link, solicitud recibida, aceptada, seguimiento a 30 días)
- [ ] Plantillas de mensaje de WhatsApp (el texto que se abre al tocar "abrir WhatsApp")
- [ ] Textos legales: compromiso de adopción, términos, privacidad
- [ ] Imagen OG del share (texto sobre la foto)
- [ ] Preguntas del cuestionario de adopción
- [ ] Motivos de rechazo
- [ ] Enums mostrados al usuario: especie, sexo, tamaño, estado, nivel de verificación
- [ ] Fechas y números vía `Intl` con el locale activo
- [ ] Meta tags y títulos de página

### Qué NO se traduce

- Contenido generado por usuarios: descripciones de animales, respuestas del cuestionario,
  nombres. Se guarda el `language` de la publicación por si algún día se quiere traducción
  automática, pero no se hace nada con eso en el MVP.

### Enums en base de datos

Los enums se guardan como **claves estables en inglés** (`dog`, `cat`, `small`, `available`,
`adopted`) y se traducen al mostrar. Nunca guardar el texto en español en la DB.

### Cuestionario

Las preguntas viven en `messages/es.json` bajo `applications.questions.*` con id estable
(`housing_type`, `has_yard`, ...). La DB guarda `{ question_id, answer }`. Cambiar el texto de una
pregunta no rompe respuestas históricas.

### Preferencia de idioma

- Usuario anónimo: cookie, detectada de `Accept-Language`, con default `es`.
- Usuario registrado: campo `locale` en el perfil. Se usa para emails y WhatsApp, que no tienen
  cookie.

### Selector de idioma

**No se construye** hasta que exista un segundo idioma. No tiene sentido un selector con una
sola opción.

## Flujo de traducción (cuando llegue)

1. `es.json` es la fuente de verdad. Siempre completo.
2. Script simple que compara claves entre `es.json` y los demás archivos y falla si faltan.
   Correrlo en CI.
3. Glosario de términos del dominio para quien traduzca (ver abajo). Un traductor sin contexto
   traduce "rescatista" como "rescuer" y "aval" como "guarantee", y ninguno sirve.
4. Herramientas tipo Crowdin/Tolgee: solo si algún día hay más de 2 idiomas y traductores externos.

## Glosario del dominio

| es | Concepto | Notas para traducir |
|---|---|---|
| rescatista | Persona que rescata y da en adopción, generalmente independiente | No es "refugio" ni "voluntario" |
| refugio | Organización con lugar físico | |
| adoptante | Quien solicita/recibe un animal | |
| ficha | Página de un animal | "listing" / "profile" según idioma |
| solicitud | Pedido formal de adopción con cuestionario | "application" |
| aval / avalado por | Nivel 3 de verificación: otro verificado responde por vos | "vouched by", no "guarantee" |
| seguimiento | Contacto post-adopción | "follow-up" |
| compromiso de adopción | Texto que ambos aceptan al cerrar | No es contrato legal; no traducir como "contract" |
| castrado | Esterilizado | "spayed/neutered" |
| chip / RENAC | Microchip obligatorio y registro nacional (Uruguay) | Concepto local; explicar, no solo traducir |
| zona | Dónde está una persona o un animal: departamento + localidad, juntos | No es una dirección ni un punto en un mapa |
| departamento | Primer nivel administrativo de Uruguay; son 19 y no cambian | "department", no "state" ni "province" |
| número a medias | El número al que se mandó un código que todavía no se confirmó | "pending number"; no "unverified phone", que es otra cosa |
| nivel 1 | La cuenta con el correo y el teléfono verificados | "level 1"; se dice en texto hasta que exista la chapita |
| quedarse con el número | Una cuenta demuestra con un código que un número verificado en otra es suyo, y la otra lo pierde (historia #25) | En código `claim`. En la interfaz, "quedarte con el número"; nunca "reclamar" ni "robar" |
| prueba | Haber escrito bien el código de un número que está en otra cuenta; vale lo que el código, 10 minutos | En código `phone_claims`. No es "proof" en el sentido de documento: es el código bien escrito |
| número perdido | El estado de una cuenta a la que otra le sacó el número: sin verificar, con el día | "lost number"; el sello dice «Sin verificar» |
| nivel 2 | La cuenta en nivel 1 con la identidad verificada con la cédula (historia #11) | "level 2"; certifica una persona real con cédula uruguaya vigente, no el nombre |
| pedido de verificación | Lo que una persona manda con la foto de su cédula y una selfie para pasar a nivel 2 | "verification request"; nunca "solicitud", que es la de adopción |
| quien administra | Persona designada por el equipo para revisar pedidos de verificación | "admin"; en la interfaz se evita "administrador" con género |
| cola de revisión | La pantalla donde quien administra resuelve los pedidos de verificación | "review queue" |
| distintivo | La chapita de cada nivel de verificación (lo que `docs/03` llama "badges") | "badge" |
| localidad | Segundo nivel de la zona. En el interior es el pueblo o la ciudad; en Montevideo, el barrio | En código `locality`. **La etiqueta cambia según el departamento**: "Barrio" en Montevideo, "Localidad" en los otros 18 (decisión 2026-09-19). Nunca "localidad o barrio" como etiqueta |
